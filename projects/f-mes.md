## Tech Stack

- **Frontend**: Next.js
- **Backend**: Spring Boot
- **Infrastructure**: AWS EC2, Linux, Nginx, Docker
- **CI/CD**: Jenkins Pipeline, Jenkins SSH Agent Plugin, Docker Registry
- **Observability**: Grafana, Loki, Tempo, Fluent Bit, Slack
- **Deployment**: Docker Image-based Deployment, SSH
- **Version Control**: Git

## 소개

제조 현장의 자재 흐름과 구매·재고 업무를 통합 관리할 수 있도록 구축한 MES 기반 업무 시스템.

입고·LOT 관리, 발주, 거래처, BOM, 기타 입출고 기능을 개발하고 CI/CD 파이프라인을 구축해 자재 관리 프로세스와 배포 운영 효율성을 함께 개선한 프로젝트.

## 주요 개발 내용

- **입고 및 LOT 관리 기능 개발**
  - 자재 입고 처리와 연계하여 LOT 발번 및 관리 기능 구현
  - 입고 데이터를 기준으로 자재 이력과 재고를 관리할 수 있도록 업무 프로세스 구성
- **발주 및 거래처 관리 기능 개발**
  - 자재 구매를 위한 발주 등록·조회 및 관리 기능 구현
  - 거래처 정보를 관리하고 발주 업무와 연계할 수 있도록 기능 구성
- **BOM 및 자재 관리 기능 개발**
  - 제품별 자재 구성 정보를 관리할 수 있도록 BOM 관리 기능 구현
  - 생산 및 자재 관리 업무에서 BOM 정보를 활용할 수 있도록 관련 기능 연계
- **재고 입출고 관리 기능 개발**
  - 입고·출고 외 발생하는 기타 입출고 업무를 처리할 수 있도록 기능 구현
  - 자재 이동 및 재고 변동 내역을 관리할 수 있도록 재고 관리 기능 구성
- **CI/CD 배포 환경 구축**
  - 애플리케이션 빌드부터 배포까지 전반적인 CI/CD 파이프라인 구축
  - 반복적인 빌드·배포 과정을 자동화하여 개발 및 배포 프로세스 개선

## CI/CD 파이프라인 구조 개선 및 배포 서버 부하 최소화

- AWS EC2 운영 서버에서 애플리케이션 빌드와 서비스 실행이 함께 수행되면서, 배포 시 서버 리소스 사용량 증가와 서비스 안정성 저하 가능성이 발생
- 운영 서버의 역할을 애플리케이션 실행에 집중시키기 위해 **CI와 CD의 책임을 분리하는 방향으로 배포 구조 재설계**
- 별도 Jenkins 환경에서 `Git Clone → Gradle Build → Docker Image Build → Registry Push` 과정을 수행하고, 운영 서버에서는 **Docker Image Pull 및 Container 실행만 담당하도록 역할 분리**
- 기존 운영 서버에서 수행하던 빌드 과정을 제거하여 배포 시 발생하던 불필요한 CPU·메모리 사용을 줄이고 서비스 실행 환경의 안정성 확보
- Docker Registry를 중심으로 빌드 결과물을 관리하여 동일한 이미지를 기준으로 배포할 수 있도록 구성하고, 빌드 환경과 실행 환경 간의 의존성 최소화
- Jenkins Pipeline과 SSH Agent Plugin을 활용해 서버 직접 접속 및 반복적인 수동 배포 작업을 자동화하고, 배포 절차를 일관된 형태로 표준화
- CI와 Runtime 환경을 분리함으로써 향후 배포 대상 서버나 서비스가 추가되더라도 기존 파이프라인 구조를 재사용할 수 있도록 확장성을 고려한 배포 체계 구축
- 결과적으로 **운영 서버 부하 감소, 배포 안정성 확보, 수동 작업 최소화 및 배포 프로세스 표준화**를 통해 운영 효율성 개선

## Next.js 선택적 모듈 빌드 구조 설계 및 빌드 프로세스 단순화

- 고객 및 배포 환경에 따라 특정 기능만 포함된 애플리케이션 빌드가 필요했으나, 기존에는 모든 기능을 포함한 단일 빌드 구조로 운영되어 불필요한 모듈 포함과 배포 산출물 관리 복잡도가 증가
- 멀티 모듈 전환, 개별 빌드 설정 분리 등 여러 방식을 검토한 결과, 현재 프로젝트 규모와 유지보수 비용을 고려하여 **기능 단위 디렉토리 구조를 표준화하고 빌드 전처리 단계에서 포함 대상을 결정하는 방식으로 설계**
- 기능별 코드 위치와 의존 관계를 정형화하여 배포 대상에 따라 필요한 모듈만 선택적으로 포함할 수 있도록 구성하고, 기존 애플리케이션 구조에 대한 변경 범위를 최소화
- Jenkins Pipeline의 빌드 전처리 단계에서 배포 프로파일에 따라 제외 대상 모듈을 자동으로 정리하도록 구성하여 **개발자가 개별 빌드 스크립트를 관리하거나 수동으로 소스를 변경하지 않아도 동일한 절차로 빌드할 수 있도록 자동화**
- 복잡한 빌드 프레임워크나 별도 프로젝트 분리를 도입하지 않고 현재 운영 환경에서 필요한 수준의 유연성을 확보하여 **구조적 복잡도와 유지보수 비용 간 균형을 고려한 빌드 방식 적용**
- 결과적으로 하나의 코드베이스를 유지하면서도 고객 및 기능 요구사항에 따른 다양한 빌드 산출물을 생성할 수 있는 구조를 확보하고, **빌드 절차 표준화와 배포 대응 효율성 개선**

## 사내 통합 Observability 및 장애 대응 체계 구축

- 사내 운영 서비스가 증가하면서 장애 발생 시 각 서비스 담당자가 개별 서버에 접근해 로그를 확인하는 방식으로 대응하고 있어, **장애 인지와 원인 분석이 담당자의 경험과 수동 확인에 의존하는 운영 구조**가 지속
- 서비스 수 증가에 따라 개별 모니터링 방식의 확장성에 한계가 있다고 판단하여, 특정 서비스에 종속되지 않고 전사 서비스에서 공통으로 사용할 수 있는 **통합 Observability 환경 구축 방향 수립**
- Grafana를 중심으로 Uptime 모니터링, 로그 수집·조회, 분산 Trace 및 장애 알림을 하나의 운영 흐름으로 연결하고, **서비스 상태 → 로그 → 요청 추적까지 단계적으로 확인할 수 있는 모니터링 구조 설계**
- Fluent Bit을 통해 각 서비스 및 컨테이너 로그를 중앙으로 수집하고 Loki에 저장하여, 담당자가 개별 서버에 접속하지 않고도 Grafana에서 **서비스·환경별 로그를 통합 조회할 수 있도록 로그 관리 체계 표준화**
- Tempo를 연계하여 서비스 간 요청 흐름과 Trace 정보를 확인할 수 있도록 구성하고, 단일 서비스 로그만으로 원인을 찾기 어려운 장애에서도 **요청 단위로 서비스 간 호출 관계를 추적할 수 있는 기반 마련**
- Uptime 기반 서비스 상태 점검과 Slack 알림을 연계하여 장애 발생 후 사용자의 신고나 담당자의 수동 확인에 의존하던 방식에서 벗어나, **서비스 이상을 조기에 인지하고 담당자가 즉시 대응할 수 있는 알림 체계 구축**
- 신규 서비스가 추가될 때 동일한 로그 수집·모니터링 기준을 적용할 수 있도록 공통 설정과 운영 방식을 정리하여 **서비스별로 개별 모니터링 환경을 구축해야 하는 관리 비용 최소화**
- 결과적으로 장애 대응 방식을 **개별 서버 확인 중심의 사후 대응에서 중앙 모니터링 기반의 선제적 탐지 및 분석 구조로 전환**하고, 서비스 증가에도 확장 가능한 사내 공통 모니터링 기반 확보
