로컬 PostgreSQL에 데이터를 넣은 뒤, 기존 운영 MySQL과 비교할 쿼리를 한 쌍씩 만들어 실행했다. 같은 고객사, 같은 기간, 같은 이관 범위로 맞춰야 비교할 수 있었다. 데이터가 맞는지 확인한 뒤에는 기존 시스템에 남아 있던 주문을 새 시스템에서 이어 처리할 수 있는지도 별도로 확인하도록 계획했다.

## 원본과 적재 결과를 대조했다

- **누락 여부.** 주문·배송 보관 이력 7개 테이블의 건수를 양쪽에서 세었다. 총 369,696행의 테이블별 건수가 일치했다.
- **변환 결과.** 기준정보는 코드 분포와 단가 합계를 비교했다. 일부 주문 상세처럼 이관 규칙상 값이 달라진 경우에는 변경의 근거와 차이를 남겼다.
- **데이터 연결.** 배송 상세가 새 주문 상세를 참조하는지, 진행 중인 주문에 상품이나 거래처가 빠져 있지 않은지 검사했다. 로컬 리허설 범위에서 누락은 없었다.

처음 매핑과 SQL을 작성한 맥락을 공유하지 않는 별도 에이전트에 대조를 맡겼다. 예를 들어 최근 주문의 거래처·상품 조합을 새 SaaS에 대입해 보니 573개 중 8개가 주문 불가로 나왔다. 사용 중지 품목과 기존 시스템에서 예외적으로 주문이 들어온 매입 거래처를 구분했고, 매입 거래처의 구분값은 전환 전에 보정할 항목으로 남겼다.

## 운영 전환 때 실행할 순서를 정했다

1. **전환 전.** 전용 기능을 배포한 뒤 로컬 리허설을 재실행한다. 옮긴 주문의 확정, 배송 배정, 주문 취소까지 실제로 실행해 확인한다.
2. **전환 시점.** 기준정보 변경을 먼저 멈추고, 전환 당일 주문·배송 입력과 외부 주문 수신을 잠시 멈춘다. 이 시점의 데이터를 최종 추출해 기준정보, 주문, 배송 순으로 적재한다.
3. **오픈 직전.** 원본과 새 DB를 다시 대조하고 현업 사용자가 로그인과 주요 화면을 확인한다. 필수 대사나 현업 확인에 실패하면 기존 시스템으로 복귀한다.
4. **오픈.** 확인을 마친 뒤 주문 수신 주소를 새 시스템으로 돌리고 실제 요청을 확인한다. 문제가 생기면 수신 주소를 원복하고 기존 시스템의 입력을 재개할 수 있게 계획했다.

**최종 상태는 조건부였다.** 로컬에서 데이터 적재와 대사를 마쳤다. 실제 업무 흐름 검증과 운영 전환은 후속 작업으로 남았다.
